# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**

## 적용 기준

**반드시 TDD를 적용해야 하는 대상**

- 비즈니스 로직
- API (라우트 핸들러, 외부 API 연동)
- 유틸 함수
- 버그 수정 (재현 테스트를 먼저 작성)

**TDD가 불필요한 대상**

- 타입 정의
- 설정 파일
- 순수 UI (마크업/스타일만 있는 프레젠테이션 컴포넌트)
- SQL / 마이그레이션

## RED → GREEN → REFACTOR 사이클

**RED**

- 하나의 동작에 대해 하나의 테스트만 작성한다.
- 작성한 테스트는 **반드시 실행하여 실패를 확인**한다.
- 실패 이유는 반드시 "기능 미구현"이어야 한다. 문법 오류나 설정 오류로 인한 실패는 RED가 아니다.

**GREEN**

- 테스트를 통과시키는 **최소한의 코드**만 작성한다. YAGNI 원칙을 따른다.
- 신규 테스트와 기존 테스트가 **모두** 통과하는지 확인한다.

**REFACTOR**

- 중복 제거, 이름 개선, 헬퍼 추출을 진행한다.
- 전 과정에서 테스트는 계속 green 상태를 유지해야 한다.
- 이 단계에서 **새로운 동작을 추가하지 않는다.**

**반복**: 다음 동작에 대해 다시 RED부터 시작한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 **삭제하고 RED부터 다시 시작한다.**
- "나중에 테스트할 수도 있으니" 참고용으로 남겨두는 것도 금지한다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 로직일수록 테스트 작성 비용이 낮다. 비용이 낮다는 것이 생략할 이유는 아니다. |
| 나중에 추가하겠다 | "나중"은 오지 않는다. 지금 추가하지 않으면 커버리지는 계속 줄어든다. |
| 시간이 없다 | 디버깅 시간이 테스트 작성 시간보다 길다. TDD는 시간을 아끼는 방법이다. |
| 삭제하면 낭비다 | 순서를 어긴 코드는 검증되지 않은 코드다. 낭비는 검증 없이 쌓인 코드 쪽이다. |
| 프로토타입이다 | 프로토타입은 코드베이스에 남는 순간 프로덕션 코드가 된다. |

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙을 우선한다.**
- 이 파일은 프로젝트별 규칙이 없을 때 적용되는 **기본값(fallback)**이다.
